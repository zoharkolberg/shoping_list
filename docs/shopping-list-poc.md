# ניסוי היתכנות — תוכנית ביצוע ובדיקות
גרסה 0.1 | 26.11.2026 | כל הבדיקות טרם בוצעו

## מטרה
אימות ההנחות הקריטיות של מסמך התכנון 0.9, לפני פיתוח האפליקציה המלאה. להשתמש בנתוני דמה בלבד. אין להרחיב OAuth scopes או להפעיל שירות בתשלום ללא אישור. שני חשבונות Google נפרדים A (בעלים) ו-B (משתתף), מחשב עם שני פרופילי דפדפן, טלפון Android/iPhone לפי זמינות. אין צורך למסור סיסמאות או אסימונים למפתח או לצ'אט.

## 1. סדר הקמת הסביבה
1. ליצור חשבון/ארגון GitHub ייעודי ולהפעיל 2FA. מאגר ציבורי shopping-list-poc. לא לפרסם נתוני בדיקה אישיים.
2. לפתוח ב-VS Code ולהפעיל שרת סטטי מקומי (למשל Live Server). לוודא כתובת מדויקת כגון http://localhost:5500 ולא לערבב localhost ו-127.0.0.1.
3. להקים פרויקט Google Cloud בשם Shopping List POC ב-console.cloud.google.com; לתעד Project ID ומספר פרויקט; לא ליצור שירותי מחשוב, מסד נתונים או חיוב מיותר. לבדוק מסלול ומכסות.
4. להפעיל Google Drive API, Google Sheets API, Google Picker API.
5. ב-Google Auth Platform: Branding (שם, כתובת תמיכה ופרטי קשר), Audience (External אם משתמשים בחשבונות Gmail אישיים), Testing ומשתמשי בדיקה A ו-B; Data Access: drive.file, openid, email. לא לבקש הרשאות Drive או Sheets גורפות. מסכי המסוף עשויים להשתנות. לבדוק דרישות Testing ומשך ההסכמה בפועל.
6. Clients: OAuth Client ID מסוג Web application. Authorized JavaScript origins: http://localhost:5500 וכן https://<github-owner>.github.io לאחר הפרסום. Origin אינו כולל נתיב המאגר. במודל Token אין צורך בשרת redirect. לא להעתיק client secret לקוד.
7. Credentials: API key ל-Picker בלבד; להגביל לשירות Picker ול-HTTP referrers המקומיים/המפורסמים ול-https://docs.google.com/* לפי תיעוד Google. להימנע ממפתח בלתי מוגבל. לבדוק בפועל referrer ו-Origin.
8. להקים שלד POC רק לאחר אישור תוכנית זו; GIS ו-Picker לפי תיעוד, REST ישיר, מסך בדיקה בסיסי. לא לבנות עדיין ממשק מוצר מלא.
9. לפרסם דרך Settings → Pages, branch main, root; לבדוק HTTPS ונתיב יחסי. אין צורך לרכוש דומיין. לבדוק OAuth ו-PWA בכתובת המפורסמת.

## 2. רכיבי אב-טיפוס מינימליים
index.html (כפתורי בדיקה ולוג מסונן), config.js (פרטים ציבוריים בלבד), auth.js, drive.js, sheets.js, picker.js, local-db.js, sync-test.js, manifest.json, sw.js, icons/. אפשר לאחד מודולים קטנים. אין קטלוג מלא; מספיקים חלב, לחם וביצים ושתי מחלקות. לוג מקומי יציג מזהי בדיקות, תוצאות וקודי שגיאה בלבד, ללא אסימונים או כתובות אישיות. להוסיף אפשרות הדמיית אובדן תשובה אחרי שהשרת עיבד כתיבה; זו אינה הדמיה מלאה של כל כשל רשת.

## 4. שערי מעבר (Go/No-Go)
- שער 1: A01–A04, D01–D06, S01, H01 עוברים. אחרת אין להתחיל פיתוח ענן מלא.
- שער 2: O01–O05, S04–S06, S08–S10, S15–S16 עוברים או שקיימת מגבלה מתועדת שאושרה במפורש. אובדן תור או ערבוב חשבונות הם חסמים.
- שער 3: למדוד S07 ו-S10 במספר חזרות (מוצע 20 לכל תרחיש), לתעד תדירות ותנאים; אפס כשל במדגם אינו הוכחת בטיחות. אם עדכון של פריט אחר נדרס או הסיכון אינו מתקבל, לבחון Developer Metadata או OperationsLog ולחזור לאישור.
- שער 4: O06–O08, D07–D08, Q01 ו-H02 לפני פרסום MVP. מכשיר שלא נבדק מסומן BLOCKED, לא PASS.
- הקמת Production לאחר הצלחת POC; לא להעביר קובצי אמת מפרויקט הבדיקה. לבצע smoke test מחדש עם credentials של Production, משום ש-drive.file ו-appProperties קשורים לזהות האפליקציה. אם נדרש אימוץ קובץ ישן, Picker ואימות Metadata.
